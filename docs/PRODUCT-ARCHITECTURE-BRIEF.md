# PITCH — Product Architecture & UX Redesign Brief
**Version:** 2026-09-25  
**Purpose:** consolidated product/UX brief for Claude / Claude Code  
**Scope:** current PITCH mobile app + Social redesign + Strava audit learnings + Open Games + Teams + Challenges + PITCH ID + Competitions/Pitch Pro

---

## 1. Executive thesis

PITCH should not be designed as “an amateur football app with a social feed”, and it should not literally copy Strava.

The product thesis is:

> **PITCH is the operating and competitive network for amateur football.**
>
> Organize your game. Find where to play. Build your team. Find opponents. Compete. Build your football identity.

“Strava for football” remains a useful shorthand for the **identity/activity/retention layer**, but it is not the full product architecture.

The critical difference is:

- Strava mainly records something the athlete already did.
- PITCH can participate **before, during and after** the match:
  - before: organize / discover / confirm / pay / challenge;
  - during: Matchday;
  - after: stats / records / identity / activity / sharing;
  - next loop: discover another game / rematch / challenge / league.

The product should therefore be designed around **football objects and football actions**, not around generic social-media primitives.

## 2. Non-negotiable product principles

### 2.1 Match is the universal core object
A match is a match regardless of origin.

A Match can originate from:
- a recurring Group;
- an Open Game;
- a Team Challenge;
- a Competition / League / Tournament.

After creation, all use the same Matchday engine:
- players;
- teams/lineups;
- check-in;
- score;
- goals;
- assists;
- MVP;
- media/highlights;
- result confirmation;
- stats;
- activity generation;
- fantasy scoring where enabled.

Do **not** build separate match systems for groups, challenges and leagues.

### 2.2 Group is not Team
**Group** = recurring community of people who organize football.  
Example: “Wednesday Football Porto”, 28 members, different teams every week.

**Team** = competitive identity with a roster.  
Example: “Pitch Founders FC”, badge, captain, squad, W-D-L record, opponents.

These must remain separate domain objects.

### 2.3 Player identity is cross-group
A player is one person across the whole PITCH ecosystem.

The same PITCH ID accumulates:
- Group matches;
- Open Games;
- Team Challenges;
- Competition matches;
- stats;
- records;
- achievements;
- teams;
- groups;
- reliability.

No per-group identity fragmentation.

### 2.4 Social is a layer, not a product silo
Do not make users “create content” to make PITCH feel alive.

The football itself should create activity.

Primary social objects should be automatically generated:
- match result;
- player performance;
- personal record;
- achievement;
- weekly leader;
- team challenge;
- team result;
- open game;
- highlight / Goal of the Week;
- competition event.

Manual photo/video/text posts can remain, but should be a minority of feed content.

### 2.5 Discovery should begin with “Find a Game”
The player’s initial intent is generally:
> “I want to play football.”

Not:
> “I want to join a digital community.”

Groups can be discoverable/open, but **game discovery is the primary marketplace surface**.

### 2.6 Do not create empty marketplaces
Team Challenge should initially work via:
- share link;
- QR;
- direct invitation;
- search by team name.

Only launch broad “Find an Opponent” discovery after sufficient local density exists.

## 3. Domain model

### 3.1 Core entities

| Entity | Meaning |
|---|---|
| Player | Permanent person / PITCH ID |
| Group | Recurring playing community |
| Team | Competitive team identity and roster |
| Match | Universal football event |
| Competition | League / tournament / structured competition |

| Highlight | Match-linked photo/video, including GOTW candidates |

PLAYER

│                         │

│
├── team_memberships ─── TEAM
│                         │
│                         ├── TEAM_CHALLENGE
│                         │
│                         └── MATCH

                          │

                          ├── stats

Suggested field:

```text

- group

- challenge
- competition
```

A match should not inherit its identity from the current group of its author/creator.

## 4. Navigation redesign

### Current
Home · Game · Matchday · Club · Compete · Profile

Problems:
- six tabs is crowded;
- “Game” and “Matchday” overlap conceptually;
- “Club” currently has no stable real-world domain meaning;
- Stats / League / Manager are mixed into Compete in a way that conflates unrelated objects;
- profile contains settings, stats, card and career without a clear information hierarchy;
- Home duplicates profile statistics rather than prioritizing next action and network activity.

### Proposed
**Home · Play · Matchday · Compete · Me**

| Tab | User intent |
|---|---|
| Home | “What is happening?” |
| Play | “Where / when am I playing?” |
| Matchday | “We are about to play / are playing.” |
| Compete | “Who are we playing against / what are we competing in?” |
| Me | “Who am I as a football player?” |

Matchday can be visually emphasized as the center tab.

## 5. HOME — activity + next action

### Purpose
Home should be global and cross-group. It should not be scoped to a selected Group by default.

Remove the persistent “current group” selector from the global header. Group/team context should be selected only where context is required.

### Header
- PITCH logo;
- greeting or compact identity;
- notifications;
- optional avatar;
- no permanent Group selector.

### Priority order
1. **Next action**
   - upcoming match;
   - payment due;
   - confirm attendance;
   - result/MVP pending;
   - challenge awaiting response.
2. **Post-match recap**
   - transient card after a match;
   - performance;
   - share CTA.
3. **Activity feed**
   - football-generated activities.
4. **Discovery inserts**
   - relevant open game;
   - challenge;
   - friend playing nearby.
5. **Weekly leaderboard / milestone cards**
   - used selectively, not as permanent dashboard clutter.

### Remove from Home
Move “Recent Summary” career totals to Me / PITCH ID.

### Example feed item types

```text
match_result
player_performance
personal_record
achievement
weekly_leader
team_challenge
team_result
open_game
highlight
gotw_candidate
gotw_winner
user_post
```

### Interaction
Keep “⚽ Golaço” as the simple binary football-native reaction.
Keep comments and share.

## 6. PLAY — games, discovery and groups

Play absorbs most of the current “Game” tab and the Group/Club operational functions.

### Top-level internal structure
Use a simple segmented control:
**Games | Groups**

### Games
Sections:
- Next game;
- My upcoming games;
- Find a Game;
- Past games.

A specific match opens a **Game Detail** page, not another bottom tab.

### Game Detail — pre-match
Contains:
- date/time/venue;
- format;
- organizer;
- confirmed / waitlist;
- price;
- payment status;
- roster;
- join / leave / cancel;
- open spots;
- organizer controls;
- “Open X spots to PITCH”.

### Find a Game
Card fields:
- format (5v5 / 6v6 / 7v7);
- area / venue;
- date/time;
- price;
- spots left;
- position needed if relevant;
- level;
- mutual players;
- organizer/group reliability.

Primary CTA:
**Join** or **Request to Join**

### Groups
Each Group has independent visibility:
- Private;
- Discoverable;
- Open.

Important:
**Group visibility and Match visibility are separate.**

A private group can open 2 spots in one specific match without becoming an open group.

### Discovery conversion
After repeated participation:
> “You played 3 matches with Wednesday Porto. Join the group?”

## 7. MATCHDAY — one stateful match engine

Matchday should be a single contextual experience that changes by match state.

### State A — before match
- roster;
- arrival/check-in;
- team draw;
- manual teams;
- goalkeeper selection;
- format;
- scoring mode;
- start match.

The current team draw screen belongs here.

### State B — live
- large score;
- game clock if enabled;
- add goal;
- add assist;
- event timeline;
- undo/edit;
- quick substitute if format needs it.

Do not overcomplicate live tracking if the group does not want granular events.

### State C — after match
- final score;
- confirm result;
- goals/assists;
- MVP voting/result;
- player performance;
- upload highlight;
- “Submit to Goal of the Week”;
- share;
- auto-generated activity.

Matchday should be the same whether the game originated in Group, Open Game, Challenge or Competition.

## 8. COMPETE — Teams, Challenges and Competitions

The current Compete structure (“Stats / League / Manager”) should be replaced.

### Proposed segmented structure
**Teams | Challenges | Competitions**

Fantasy/Manager becomes contextual within the relevant Group/Competition instead of a top-level product category.

### Teams
If user has no Team:
- Create Team;
- Join via invite.

If user has Team:
- badge/name;
- W-D-L;
- form;
- squad;
- next opponent;
- recent results;
- records;
- team stats;
- trophies.

### Create Team
Fields:
- name;
- badge;
- colors;
- city;
- home venue;
- preferred format;
- captain;
- roster invitations.

### Challenges
Incoming / outgoing / completed.

Challenge proposal:
- opponent;
- format;
- date/time;
- venue;
- duration;
- pitch cost / split;
- optional level note.

Actions:
- Accept;
- Counter;
- Decline.

Accepted challenge creates a normal Match.

After result:
- both captains confirm;
- stats update;
- Team W-D-L updates;
- activity created;
- Rematch CTA.

### Find Opponent
Do not launch as an empty marketplace.

Phase 1:
- team URL;
- QR;
- team name search;
- invitation.

Phase 2 after density:
- date;
- format;
- distance;
- level;
- availability;
- venue.

### Competitions
Competition page can contain:
- table;
- fixtures;
- results;
- teams;
- player stats;
- fantasy;
- public following;
- sponsors/media in Pitch Pro.

## 9. ME — PITCH ID / Football Passport

Profile should stop being mainly “card + settings”.

It becomes the permanent player identity.

### Above the fold
- photo;
- name;
- position;
- city;
- PITCH Card;
- headline career stats.

### Core sections
- Career;
- Recent form;
- Records;
- Achievements;
- Match history;
- Teams;
- Groups;
- reliability;
- friends;
- media/highlights.

### Career metrics
Examples:
- matches;
- goals;
- assists;
- MVPs;
- G+A per game;
- attendance;
- wins if meaningful and comparable.

### Automatic personal records
PITCH should calculate these from match history:
- most goals in a match;
- most assists in a match;
- longest scoring streak;
- longest attendance streak;
- highest seasonal MVP count;
- milestones such as 25 / 50 / 100 matches.

Users should not manually “register” records.

### Calendar
Keep the current calendar/progress concept, but make it useful:
- dots for match days;
- click date → match detail;
- season/month switch;
- streak visualization.

### Achievements
Use restraint.
Achievements should represent meaningful football milestones or time-bounded challenges, not dozens of arbitrary badges.

### Reliability
For Open Games:
- matches played;
- attendance percentage;
- member since;
- mutual players.

Avoid subjective star ratings initially.

### Settings
Move all utilities behind a gear/settings page:
- contact;
- MB Way/payment settings;
- group settings;
- language;
- theme;
- security.

Do not let settings dominate the main player profile.

## 11. Goal of the Week and Challenges

The current database concept exists but should be implemented as a real time-bounded challenge.

### Goal of the Week
Flow:
1. Match happens.
2. Player uploads a video highlight tied to Match + Player.
3. Select “Submit to Goal of the Week”.
4. Voting window opens.
5. Winner closes on a fixed cadence.
6. Winner receives permanent achievement.
7. Result generates Activity.
8. Highlight can be reused in PITCH social/Instagram content.

### Future challenge framework
Could support:
- play X matches this month;
- attendance streak;
- Team wins;
- Group participation;
- city/community challenges.

Challenges must be limited and meaningful.

## 12. Friends vs Follow

Keep **bilateral friendship** for Players.

Reason:
PITCH is based primarily on real football relationships and recurring local groups, not celebrity/creator following.

Future:
Allow **Follow** for non-person entities:
- Team;
- Competition;
- Club/Venue;
- League.

This lets spectators follow a Team or League without becoming members.

## 13. Guest / unregistered players

Add:
**“Add guest player”**

A guest can:
- appear in roster;
- receive match stats;
- have a temporary identity.

After the match:
> “Invite Ricardo to claim this match.”

If Ricardo creates PITCH:
- claim guest identity;
- retroactively add the match to PITCH ID.

This reduces onboarding friction and becomes an acquisition mechanism.

## 17. Fantasy / PITCH Manager

PITCH Manager should remain, but become contextual.

Examples:
- a Group can enable Manager/Fantasy;
- a Competition can enable Fantasy.

Fantasy consumes Match events/stats.

It should not determine the core information architecture.

Possible access:
- inside Group page;
- inside Competition page;
- shortcut card on Home when there is an active fantasy round.

## 19. Four core product loops

### Organizer Loop
Create Match → confirm players → payment/waitlist → play → next Match.

### Discovery Loop
Group opens spots → Player finds game → plays → meets people → joins Group → finds more games.

### Competition Loop
Create Team → challenge opponent → Match → result/history → rematch → Competition.

### Identity Loop
Play → stats → records → achievements → activity → desire to play again.

These loops should reinforce one another.

## 20. Design / visual system recommendations

Keep:
- dark navy base;
- acid lime signature;
- current football-card personality.

Change:
- use lime primarily for action / active state, not everywhere;
- reduce nested cards inside cards;
- reduce low-contrast tiny copy;
- use clearer vertical hierarchy;
- avoid too many persistent modules on Home;
- reserve italic display type for branded moments, not all key labels;
- standardize radius and spacing;
- minimum 44–48px touch targets;
- prefer one primary CTA per card;
- use chips for Group / Team / Competition context;
- use contextual headers instead of one global Group selector.

Suggested spacing:
- 16px horizontal page margin;
- 8px spacing grid;
- 12–16px card radius;
- 16–20px major section spacing.

Suggested card states:
- neutral = standard navy card;
- action required = lime edge / icon;
- destructive = red only;
- completed = muted/green confirmation;
- premium/fantasy = optional distinct but restrained accent.

## 25. Final product definition

PITCH began by solving:

> “Who is playing this week?”

The product can expand into:

> Where can I play?  
> Who do I play with?  
> Who can our team play against?  
> How are we performing?  
> What is my football history?  
> What is happening in my football network?  
> What is my next match?

The strategic product is not:
- merely a pickup-game organizer;
- a generic social network;
- a Strava clone;
- only a fantasy game;
- only a league-management platform.

Those are layers or use cases.

The larger product is:

> **The digital infrastructure for amateur football life.**

And the object that connects it all is:

> **MATCH**
